Attribute-Based Access Control (ABAC) in Keycloak

Learn how to build fine-grained, dynamic, and context-aware security policies using user, resource, and environment attributes in Keycloak.

8. Alternative Approaches to Embedding Permissions

When implementing access control with Keycloak, a key architectural decision is where and how permissions are stored and validated. Below is a comparison of six distinct approaches to managing permission data, evaluated against your current ABAC setup.

Note: This analysis is based on your current ABAC tutorial setup where the token contains raw user attributes (department, clearance_level) and Keycloak's PDP evaluates policies at request time.

1. 🏷️ Raw User Attributes (ABAC Claims) — Current Approach

"clearance_level": "1",
"department": "eng"

How it works: User attributes are mapped into the access token via protocol mappers. The resource server (or Keycloak PDP) evaluates policies at request time.

Pros Cons
Flexible — policy changes don't require new tokens Token doesn't tell you what the user can do, only who they are
Centralized policy management
Small, stable token size		 Resource server must know the policy rules to enforce them
Requires a PDP call or local policy engine for every access decision
Verdict: ✅ Great for complex, dynamic policies. This is the "proper ABAC" approach.

2. 👤 Roles in Token (RBAC Claims)

"realm_access": { "roles": ["manager", "hr-viewer"] },
"resource_access": { "document-service-api": { "roles": ["doc-editor"] } }

How it works: Assign fine-grained client roles (e.g., hr-doc-reader, eng-doc-writer). The access token carries these roles directly.

Pros Cons
Simple to check — token.roles.includes("hr-viewer") Role explosion — us-hr-manager-l3, eu-eng-viewer-l2, etc.
No external PDP call needed
Well-understood pattern		 Static — changing a policy means reassigning roles to users
Can't encode contextual rules (time, network, etc.)
Verdict: ⚠️ Good for simple cases, but doesn't scale. This is exactly why ABAC exists.

3. 🎫 Permissions / Entitlements in Token (RPT — Requesting Party Token)

"authorization": {
  "permissions": [
    {
      "rsid": "a1b2c3d4",
      "rsname": "Secret HR Report",
      "scopes": ["read"]
    }
  ]
}

How it works: Request a full RPT. Keycloak evaluates all policies at token request time and embeds the granted permissions directly into a new token.

Requesting an RPT (UMA Grant) 
# Request an RPT instead of a decision
curl -H "Authorization: Bearer <ACCESS_TOKEN>" \
     -d "grant_type=urn:ietf:params:oauth:grant-type:uma-ticket" \
     -d "audience=document-service-api" \
     -X POST http://localhost:8080/realms/abac-realm/protocol/openid-connect/token
Pros Cons
Token explicitly says "you CAN access Secret HR Report with scope read" Token bloat — grows with number of resources
Resource server just checks the RPT locally; no policy evaluation needed
UMA 2.0 standard-compliant		 Must re-request RPT when permissions change
Added round-trip to Keycloak; more complex token lifecycle
Verdict: ✅ Arguably the best hybrid — ABAC policies decide, but the result is a portable permission list.

4. 🔒 OAuth2 Scopes as Permissions

"scope": "profile email documents:read documents:write reports:read"

How it works: Use OAuth2 scopes to represent fine-grained permissions. The client requests specific scopes, and Keycloak decides which to grant.

Pros Cons
Standard OAuth2 — works with any resource server Scopes are coarse, not resource-specific
Easy to check — scope.includes("documents:read")
No custom claims needed		 Can't distinguish "read HR docs" from "read Eng docs"
Scope explosion similar to role explosion
Verdict: ⚠️ Better suited for API-level access control, not resource-level ABAC.

5. 🧩 Custom Permission Claims via Script Mapper

"permissions": {
  "documents": ["read", "write"],
  "reports": ["read"],
  "admin-panel": []
}

How it works: Use a Keycloak Script Mapper to compute a permission map at token-generation time, injecting it as a custom claim.

Pros Cons
Token is self-contained — no PDP call at runtime Permissions are frozen at token-issue time
Resource server has zero policy knowledge
Fully customizable format		 Script runs on every token issuance (perf cost)
Can't encode dynamic context changing per-request
Verdict: ⚠️ Pragmatic for semi-static permissions, but loses ABAC's dynamic nature.

6. 🌐 External Authorization (No Permissions in Token)

Token: contains identity only (sub, name, email)
↓
Request hits your API
↓
API calls external PDP (OPA, Cedar, Keycloak) with {user, resource, action, context}
↓
PDP returns allow/deny

How it works: Every access decision is delegated to an external Policy Decision Point (PDP) at request time. Common engines include OPA, AWS Cedar, or Keycloak's token endpoint.

Pros Cons
Token stays small and simple Every request requires a PDP round-trip (latency)
Permissions are always real-time, never stale
Full context available (time, IP, device)		 PDP becomes critical dependency (availability risk)
More infrastructure to manage
Verdict: ✅ Best for high-security, dynamic environments. This matches the current Keycloak flow using response_mode=decision.

Summary Comparison

Approach Token Size Real-time? Complexity Best For
ABAC attributes (current) Small Policy-dependent Medium Dynamic, attribute-driven rules
Roles (RBAC) Small No Low Simple permission models
RPT (Permissions in token) Large At issuance Medium Portable, pre-evaluated grants
OAuth2 Scopes Small No Low API-level gates
Custom Permission Claims Medium No Medium Semi-static computed permissions
External PDP Minimal Yes High High-security, real-time decisions
Recommendation: Your current setup is very well designed. It uses a hybrid of:
  1. Attributes in the token (department, clearance_level) — so the PDP has user context.
  2. Keycloak PDP evaluation (response_mode=decision) — so policies are centralized and dynamic.
  3. Runtime claims (claim_token with network_location) — so environment context flows in.

The most natural evolution would be to switch from response_mode=decision to full RPT tokens (Approach #3). That way your resource server gets a self-contained token with explicit permissions, eliminating the per-request PDP call while still benefiting from ABAC policy evaluation.
