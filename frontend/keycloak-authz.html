Attribute-Based Access Control (ABAC) in Keycloak

Learn how to build fine-grained, dynamic, and context-aware security policies using user, resource, and environment attributes in Keycloak.

2. Keycloak Authorization Services

Keycloak supports fine-grained authorization policies under its Authorization Services. This is distinct from simple client scopes and role claims. It allows you to build a true centralized PDP.

Key concept: Think of Keycloak Authorization Services as an authorization layer that sits on top of authentication. Authentication answers "who is the user?" while the auth service answers "can this authenticated user perform this action on this protected thing under these conditions?"

How the Auth Service Works

In practice, your API or application is registered in Keycloak as a resource server. That resource server sends authorization requests to Keycloak, and Keycloak evaluates the request by combining protected resources, allowed scopes, decision policies, and the permission objects that bind them together.

Key Components:

  • Resource Servers: The application client representing the API or service you want to protect.
  • Resources: The assets being protected (e.g., specific URLs, documents, files, or generic APIs) which can have their own custom attributes.
  • Authorization Scopes: The actions allowed on resources (e.g., read, write, delete).
  • Policies: The conditions that must be met to grant access (e.g., JavaScript scripts, time rules, role requirements).
  • Permissions: The binding elements that tie together Resources, Scopes, and Policies.

The Four Pillars: Resource, Scope, Policy, Permission

These four concepts are the core modeling units inside Keycloak Authorization Services. If they are designed cleanly, ABAC and other fine-grained models become much easier to reason about.

1

Resource

A resource is the thing being protected: an API endpoint, document, invoice, report, or business object. In Keycloak, resources can also carry attributes like ownerDepartment, region, or classification.

2

Scope

A scope is the action requested on the resource, such as read, create, approve, or delete. Scopes keep actions separate from the resource itself.

3

Policy

A policy defines the rule used to make the decision. It can evaluate roles, groups, user attributes, resource attributes, time windows, networks, or JavaScript logic for dynamic ABAC checks.

4

Permission

A permission is the binding layer. It connects one or more resources and scopes to one or more policies, telling Keycloak exactly when access should be granted.

Simple mental model: Permission = Resource + Scope + Policy
Example: Allow read on employee-record only when the policy confirms the user's department and clearance match the resource requirements.
