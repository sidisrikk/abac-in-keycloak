Attribute-Based Access Control (ABAC) in Keycloak

Learn how to build fine-grained, dynamic, and context-aware security policies using user, resource, and environment attributes in Keycloak.

1. Introduction to ABAC vs RBAC

Access control is the cornerstone of modern security architecture. Traditionally, Role-Based Access Control (RBAC) has been the standard. However, as business requirements grow in complexity, RBAC's limitations become evident, giving rise to Attribute-Based Access Control (ABAC).

R

Role-Based Access Control (RBAC)

Grants permissions based on pre-defined roles (e.g., Admin, Manager, Employee). While simple to start, it leads to "Role Explosion" when you need parameters like US-Sales-Manager, EU-HR-Manager, etc.

A

Attribute-Based Access Control (ABAC)

Grants permissions based on a combination of Subject, Resource, and Environment attributes. Extremely flexible, allowing complex rules (e.g., "HR Managers can view records from the US during office hours").

The ABAC Architecture (XACML Reference Model)

Standard ABAC systems follow the XACML framework, which defines specific functional entities to separate policy definition, evaluation, and enforcement:

graph LR subgraph PEP [PEP: Policy Enforcement Point] App[Your Application] end subgraph Keycloak [PDP: Policy Decision Point] KC[Keycloak AuthZ Engine] end subgraph PIP [PIP: Policy Information Point] DB[(User Attributes / DB)] end subgraph PAP [PAP: Policy Administration Point] Console[Keycloak Admin Console] end App -->|1. Request Access| KC KC -->|2. Fetch Attributes| DB DB -->|3. Return Attributes| KC Console -->|Configure Policies| KC KC -->|4. Permit / Deny| App
Note: In this setup, Keycloak acts as both the PDP (evaluating decisions) and the PAP (where you manage policies). Your client application acts as the PEP, sending tokens and intercepting traffic to enforce the decision.

2. Keycloak Authorization Services

Keycloak supports fine-grained authorization policies under its Authorization Services. This is distinct from simple client scopes and role claims. It allows you to build a true centralized PDP.

Key concept: Think of Keycloak Authorization Services as an authorization layer that sits on top of authentication. Authentication answers "who is the user?" while the auth service answers "can this authenticated user perform this action on this protected thing under these conditions?"

How the Auth Service Works

In practice, your API or application is registered in Keycloak as a resource server. That resource server sends authorization requests to Keycloak, and Keycloak evaluates the request by combining protected resources, allowed scopes, decision policies, and the permission objects that bind them together.

Key Components:

  • Resource Servers: The application client representing the API or service you want to protect.
  • Resources: The assets being protected (e.g., specific URLs, documents, files, or generic APIs) which can have their own custom attributes.
  • Authorization Scopes: The actions allowed on resources (e.g., read, write, delete).
  • Policies: The conditions that must be met to grant access (e.g., JavaScript scripts, time rules, role requirements).
  • Permissions: The binding elements that tie together Resources, Scopes, and Policies.

The Four Pillars: Resource, Scope, Policy, Permission

These four concepts are the core modeling units inside Keycloak Authorization Services. If they are designed cleanly, ABAC and other fine-grained models become much easier to reason about.

1

Resource

A resource is the thing being protected: an API endpoint, document, invoice, report, or business object. In Keycloak, resources can also carry attributes like ownerDepartment, region, or classification.

2

Scope

A scope is the action requested on the resource, such as read, create, approve, or delete. Scopes keep actions separate from the resource itself.

3

Policy

A policy defines the rule used to make the decision. It can evaluate roles, groups, user attributes, resource attributes, time windows, networks, or JavaScript logic for dynamic ABAC checks.

4

Permission

A permission is the binding layer. It connects one or more resources and scopes to one or more policies, telling Keycloak exactly when access should be granted.

Simple mental model: Permission = Resource + Scope + Policy
Example: Allow read on employee-record only when the policy confirms the user's department and clearance match the resource requirements.

3. Implementing ABAC

To implement ABAC in Keycloak, attributes must be populated across three logical layers:

  1. Subject (User) Attributes: Defined in Keycloak on the User profiles (e.g., department, clearance_level).
  2. Resource Attributes: Defined inside Keycloak Authorization tab under Resources (e.g., department = HR, classification = Level 3).
  3. Context/Environment Attributes: Provided at runtime within the evaluation context (e.g., Client Network IP, Current Time).

JavaScript Policies: Keycloak's Dynamic Engine

To write true attribute matching rules in Keycloak, you use JavaScript Policies. These run directly on the Keycloak JVM server. Here is how Keycloak parses the attributes at runtime:

keycloak-attributes-retrieval.js 
// Fetch the context
var context = $evaluation.getContext();
// Subject attributes
var userAttrs = context.getIdentity().getAttributes();
var userDept = userAttrs.getValue('department').asString();

// Resource attributes
var resourceAttrs = $evaluation.getPermission().getResource().getAttributes();
var resourceDept = resourceAttrs.getValue('department').asString();

// Perform comparison
if (userDept === resourceDept) {
    $evaluation.grant();
}

Step 9: Testing the Policy Execution

You can verify access rights using the Keycloak Authorization Endpoint. First obtain an access token that carries the mapped user attributes, then request an authorization decision for the protected resource.

1. Authenticate Alice (Department: HR, Clearance: 3)

# Get Access Token for Alice
curl -d "client_id=document-service-api" \
     -d "username=alice" \
     -d "password=password" \
     -d "grant_type=password" \
     -d "scope=openid profile abac-attributes" \
     -d "client_secret=<YOUR_CLIENT_SECRET>" \
     -X POST http://localhost:8080/realms/abac-realm/protocol/openid-connect/token

If you assigned abac-attributes as a default client scope in Step 4, the explicit scope line is optional. Keep it if you want the request to be unambiguous. Before moving on, decode the token and confirm it includes department and clearance_level.

2. Query keycloak for Resource Authorization Decisions

# Alice requests access to "Secret HR Report" (Clearance 3 required, Dept HR required)
# Push runtime environment claims through claim_token. Raw form fields like
# network_location=office are not exposed to JavaScript policies.
CLAIM_TOKEN=$(printf '%s' '{"network_location":["office"]}' | base64 -w0)

curl -H "Authorization: Bearer <ALICE_ACCESS_TOKEN>" \
     -d "grant_type=urn:ietf:params:oauth:grant-type:uma-ticket" \
     -d "audience=document-service-api" \
     -d "response_mode=decision" \
     -d "permission=Secret HR Report" \
     -d "claim_token=${CLAIM_TOKEN}" \
     -d "claim_token_format=urn:ietf:params:oauth:token-type:jwt" \
     -X POST http://localhost:8080/realms/abac-realm/protocol/openid-connect/token

If Keycloak exposes the mapped user claims and the pushed runtime claim correctly, Alice should receive {"result":true}. If access is denied, inspect the Keycloak container logs because the bundled policy now prints the user attribute keys, context attribute keys, and normalized values it actually evaluated.

3. Repeat with Bob (Department: Eng, Clearance: 1)

When Bob requests access to the Secret HR Report, Keycloak's PDP should return 403 Forbidden because his department does not match and his clearance is insufficient.

If you need to troubleshoot the evaluation, inspect the server logs with docker compose logs -f keycloak from the lab-code/ directory. The bundled policy logs lines such as User Attribute Keys, Context Attribute Keys, and the normalized department/network values to show what Keycloak actually made available during authorization.

6. Evolving to RPT: Self-Contained Permission Tokens

In Step 9, you used response_mode=decision which returns a simple {"result":true} or 403 Forbidden. This works well, but it means your resource server must call Keycloak's token endpoint on every single request to get an authorization decision. The next evolution is to use Requesting Party Tokens (RPT) — a UMA 2.0 standard where Keycloak evaluates all your ABAC policies and embeds the granted permissions directly into a new JWT.

Decision Mode vs RPT: What Changes?

?

Decision Mode (Current)

Returns a simple boolean answer: {"result":true} or HTTP 403. Your resource server must ask Keycloak every time a user accesses a protected resource. Fast for single checks, but adds latency per-request.

🎫

RPT Mode (Evolution)

Returns a full JWT token with an authorization claim listing every resource and scope the user is permitted. Your resource server can validate this token locally — no per-request PDP call needed.

Architecture: How RPT Changes the Flow

sequenceDiagram participant Client as Client / PEP participant KC as Keycloak PDP participant API as Resource Server Client->>KC: 1. Authenticate (get access token) KC-->>Client: Access Token (with ABAC attributes) Client->>KC: 2. Request RPT (UMA grant + permission) Note over KC: Evaluates ABAC policies
against user attrs, resource attrs,
and environment context KC-->>Client: RPT (JWT with embedded permissions) Client->>API: 3. Request resource with RPT Note over API: Validates RPT signature locally
Checks authorization.permissions claim
No call back to Keycloak needed API-->>Client: 4. Resource data
Key Insight: The RPT is a regular JWT signed by Keycloak. Your resource server only needs Keycloak's public key to verify it — no network round-trip to the PDP on every request. The ABAC evaluation happens once when the RPT is issued.

Step-by-Step: Requesting an RPT

Using the same setup from the hands-on lab, here is how to switch from decision mode to RPT mode.

1. Get an Access Token (Same as Before)

Authenticate Alice 
# Get Access Token for Alice (same as Step 9)
curl -s -d "client_id=document-service-api" \
     -d "username=alice" \
     -d "password=password" \
     -d "grant_type=password" \
     -d "scope=openid profile abac-attributes" \
     -d "client_secret=<YOUR_CLIENT_SECRET>" \
     -X POST http://localhost:8080/realms/abac-realm/protocol/openid-connect/token \
     | jq -r '.access_token'

# Store it
ACCESS_TOKEN="<paste token here>"

2. Request an RPT (Remove response_mode=decision)

The only difference from Step 9 is that you omit the response_mode=decision parameter. Without it, Keycloak returns a full RPT instead of a boolean.

Request RPT for a Specific Resource 
# Request RPT for "Secret HR Report"
CLAIM_TOKEN=$(printf '%s' '{"network_location":["office"]}' | base64 -w0)

curl -s -H "Authorization: Bearer ${ACCESS_TOKEN}" \
     -d "grant_type=urn:ietf:params:oauth:grant-type:uma-ticket" \
     -d "audience=document-service-api" \
     -d "permission=Secret HR Report" \
     -d "claim_token=${CLAIM_TOKEN}" \
     -d "claim_token_format=urn:ietf:params:oauth:token-type:jwt" \
     -X POST http://localhost:8080/realms/abac-realm/protocol/openid-connect/token \
     | jq -r '.access_token'

# This returns a full JWT (the RPT), not {"result":true}
Notice: The response field is access_token — the RPT is returned as a new access token that replaces your original one. It contains everything the original token had, plus an authorization block with granted permissions.

3. Request RPT for ALL Permitted Resources

You can also omit the permission parameter entirely. Keycloak will evaluate all resources and return permissions for every resource the user is allowed to access.

Request RPT for All Resources 
# Request RPT for ALL resources the user can access
CLAIM_TOKEN=$(printf '%s' '{"network_location":["office"]}' | base64 -w0)

curl -s -H "Authorization: Bearer ${ACCESS_TOKEN}" \
     -d "grant_type=urn:ietf:params:oauth:grant-type:uma-ticket" \
     -d "audience=document-service-api" \
     -d "claim_token=${CLAIM_TOKEN}" \
     -d "claim_token_format=urn:ietf:params:oauth:token-type:jwt" \
     -X POST http://localhost:8080/realms/abac-realm/protocol/openid-connect/token \
     | jq -r '.access_token'

4. Decode the RPT and Inspect Permissions

Decode the RPT JWT (using jwt.io or the command below) and you will see the new authorization claim:

Decode RPT 
# Decode the RPT payload (middle segment of the JWT)
echo "${RPT}" | cut -d'.' -f2 | base64 -d 2>/dev/null | jq .

What the RPT Looks Like

The decoded RPT contains everything your original access token had, plus an authorization block:

RPT Payload (Key Fields) 
{
  "exp": 1780731595,
  "iss": "http://localhost:8080/realms/abac-realm",
  "sub": "...",
  "azp": "document-service-api",
  "preferred_username": "alice",
  "department": "hr",
  "clearance_level": "3",

  "authorization": {
    "permissions": [
      {
        "rsid": "a1b2c3d4-...",
        "rsname": "Secret HR Report",
        "scopes": ["read", "write", "delete"]
      }
    ]
  }
}
Key Fields in authorization.permissions:
  • rsid — The unique ID of the resource in Keycloak
  • rsname — The human-readable name (e.g., "Secret HR Report")
  • scopes — The granted scopes (e.g., ["read", "write"]). Empty if no scopes were defined on the resource.

How the Resource Server Uses the RPT

Your API only needs to do two things — no Keycloak calls at runtime:

resource-server-middleware.js (Pseudocode) 
// 1. Verify the RPT signature using Keycloak's public key
//    (fetched once from the JWKS endpoint and cached)
const decoded = jwt.verify(rptToken, keycloakPublicKey, {
  issuer: 'http://localhost:8080/realms/abac-realm',
  audience: 'document-service-api'
});

// 2. Check if the requested resource AND scope are in the permissions list
const permissions = decoded.authorization?.permissions || [];

function hasPermission(resourceName, requiredScope) {
  return permissions.some(p =>
    p.rsname === resourceName &&
    p.scopes?.includes(requiredScope)
  );
}

// Example: Check read access
if (hasPermission('Secret HR Report', 'read')) {
  // ✅ Can read
}

// Example: Check write access
if (hasPermission('Secret HR Report', 'write')) {
  // ✅ Can write (only managers)
} else {
  // ❌ 403 — user can read but not write
  return res.status(403).json({ error: 'Write access denied' });
}

When to Refresh the RPT

Since the RPT is a JWT with an exp (expiration) claim, permissions are frozen until the token expires. Request a new RPT when:

  • The RPT expires (same lifetime as the access token, typically 5–15 minutes)
  • The user's roles or attributes change and you need updated permissions
  • You need to re-evaluate with different environment context (e.g., network changed)

7. RPT Request Strategies: One Call vs Per-Resource

A common question when using RPTs: should you request permissions for all resources at once, or one resource at a time? The answer depends on your application's scale and requirements.

Strategy A: All Resources at Once (Recommended for Most Apps)

Omit the permission parameter entirely — Keycloak evaluates every resource and returns all permissions the user is granted:

Request RPT for All Resources 
# Single call → RPT with ALL permitted resources and scopes
curl -s -H "Authorization: Bearer ${ACCESS_TOKEN}" \
     -d "grant_type=urn:ietf:params:oauth:grant-type:uma-ticket" \
     -d "audience=document-service-api" \
     -X POST http://localhost:8080/realms/abac-realm/protocol/openid-connect/token \
     | jq -r '.access_token'

The resulting RPT contains every resource Alice can access:

RPT with All Permissions (Alice) 
"authorization": {
  "permissions": [
    {
      "rsname": "Secret HR Report",
      "scopes": ["read", "write", "delete"]
    },
    {
      "rsname": "HR Handbook",
      "scopes": ["read", "write"]
    },
    {
      "rsname": "Company Newsletter",
      "scopes": ["read"]
    }
  ]
}
This is the recommended approach for apps with a manageable number of resources (under ~50). One authentication call + one RPT call = done. The token carries all permissions, and your resource server validates locally with zero Keycloak round-trips.

Strategy B: Per-Resource RPT (For Large-Scale Systems)

Specify the permission parameter to request access for a specific resource only. This is useful when requesting all resources would be impractical.

Request RPT for One Resource 
# Only evaluate permissions for the resource the user is accessing
curl -s -H "Authorization: Bearer ${ACCESS_TOKEN}" \
     -d "grant_type=urn:ietf:params:oauth:grant-type:uma-ticket" \
     -d "audience=document-service-api" \
     -d "permission=Secret HR Report" \
     -X POST http://localhost:8080/realms/abac-realm/protocol/openid-connect/token \
     | jq -r '.access_token'

When Per-Resource Is Necessary

📦

Token Size Limits

An app with 5,000 documents would generate an RPT with 5,000 permission entries. This token could exceed 50KB+ — too large for HTTP headers (most servers cap at 8–16KB). Per-resource RPTs stay small and focused.

🌐

Different Context Per Resource

The claim_token for environment context is sent once per RPT request. If Resource A needs network_location=office and Resource B needs network_location=branch-tokyo, you need separate requests with different context.

⏱️

Lazy Evaluation (Performance)

A dashboard listing 200 documents where users typically open 2–3. Evaluating all 200 policies at login adds latency. Instead, request permissions per-document when the user clicks — instant login, tiny per-click cost.

🔒

Principle of Least Privilege

If a token is intercepted, a per-resource RPT reveals access to 1 resource. An all-at-once RPT reveals the user's entire permission map. Security-sensitive systems prefer minimal exposure.

Strategy C: Hybrid — RPT Upgrade (Best of Both)

Keycloak supports appending permissions to an existing RPT. Start with common resources at login, then upgrade the token when the user accesses additional resources:

Hybrid RPT Upgrade Flow 
# Step 1: Login → get RPT with commonly-accessed resources
RPT=$(curl -s -H "Authorization: Bearer ${ACCESS_TOKEN}" \
     -d "grant_type=urn:ietf:params:oauth:grant-type:uma-ticket" \
     -d "audience=document-service-api" \
     -d "permission=Dashboard" \
     -d "permission=User Profile" \
     -X POST http://localhost:8080/realms/abac-realm/protocol/openid-connect/token \
     | jq -r '.access_token')

# RPT now contains: Dashboard + User Profile permissions

# Step 2: User clicks on a specific document → upgrade the RPT
UPGRADED_RPT=$(curl -s -H "Authorization: Bearer ${RPT}" \
     -d "grant_type=urn:ietf:params:oauth:grant-type:uma-ticket" \
     -d "audience=document-service-api" \
     -d "permission=Secret HR Report" \
     -X POST http://localhost:8080/realms/abac-realm/protocol/openid-connect/token \
     | jq -r '.access_token')

# UPGRADED_RPT now contains: Dashboard + User Profile + Secret HR Report
# The old permissions are preserved and the new one is appended
Key Detail: When you submit an existing RPT as the Bearer token in a new UMA request, Keycloak merges the old permissions with the newly evaluated ones. You get a single token that grows incrementally as the user navigates your application.

Decision Guide: Which Strategy to Use

Scenario Strategy Why
App with < 50 resources All at once ✅ Simple, small token, fast
App with 1,000+ resources Per-resource Token size limits, evaluation cost
Same context for all resources All at once ✅ No reason to split
Different context per resource Per-resource Different claim_token needed
Dashboard → user picks one item Hybrid upgrade Fast login, grow token on demand
Mobile app / limited bandwidth All at once ✅ Fewer HTTP round-trips
High-security / zero-trust Per-resource Minimal exposure if token leaks
Bottom Line: For most applications, request all resources at once. The per-resource and hybrid approaches exist for edge cases involving scale, security, or varying context. Your two-step flow remains: 1 authentication call + 1 RPT call = done.

1. 🏷️ Raw User Attributes (ABAC Claims) — Current Approach

"clearance_level": "1",
"department": "eng"

How it works: User attributes are mapped into the access token via protocol mappers. The resource server (or Keycloak PDP) evaluates policies at request time.

Pros Cons
Flexible — policy changes don't require new tokens Token doesn't tell you what the user can do, only who they are
Centralized policy management
Small, stable token size		 Resource server must know the policy rules to enforce them
Requires a PDP call or local policy engine for every access decision
Verdict: ✅ Great for complex, dynamic policies. This is the "proper ABAC" approach.

2. 👤 Roles in Token (RBAC Claims)

"realm_access": { "roles": ["manager", "hr-viewer"] },
"resource_access": { "document-service-api": { "roles": ["doc-editor"] } }

How it works: Assign fine-grained client roles (e.g., hr-doc-reader, eng-doc-writer). The access token carries these roles directly.

Pros Cons
Simple to check — token.roles.includes("hr-viewer") Role explosion — us-hr-manager-l3, eu-eng-viewer-l2, etc.
No external PDP call needed
Well-understood pattern		 Static — changing a policy means reassigning roles to users
Can't encode contextual rules (time, network, etc.)
Verdict: ⚠️ Good for simple cases, but doesn't scale. This is exactly why ABAC exists.

3. 🎫 Permissions / Entitlements in Token (RPT — Requesting Party Token)

"authorization": {
  "permissions": [
    {
      "rsid": "a1b2c3d4",
      "rsname": "Secret HR Report",
      "scopes": ["read"]
    }
  ]
}

How it works: Request a full RPT. Keycloak evaluates all policies at token request time and embeds the granted permissions directly into a new token.

Requesting an RPT (UMA Grant) 
# Request an RPT instead of a decision
curl -H "Authorization: Bearer <ACCESS_TOKEN>" \
     -d "grant_type=urn:ietf:params:oauth:grant-type:uma-ticket" \
     -d "audience=document-service-api" \
     -X POST http://localhost:8080/realms/abac-realm/protocol/openid-connect/token
Pros Cons
Token explicitly says "you CAN access Secret HR Report with scope read" Token bloat — grows with number of resources
Resource server just checks the RPT locally; no policy evaluation needed
UMA 2.0 standard-compliant		 Must re-request RPT when permissions change
Added round-trip to Keycloak; more complex token lifecycle
Verdict: ✅ Arguably the best hybrid — ABAC policies decide, but the result is a portable permission list.

4. 🔒 OAuth2 Scopes as Permissions

"scope": "profile email documents:read documents:write reports:read"

How it works: Use OAuth2 scopes to represent fine-grained permissions. The client requests specific scopes, and Keycloak decides which to grant.

Pros Cons
Standard OAuth2 — works with any resource server Scopes are coarse, not resource-specific
Easy to check — scope.includes("documents:read")
No custom claims needed		 Can't distinguish "read HR docs" from "read Eng docs"
Scope explosion similar to role explosion
Verdict: ⚠️ Better suited for API-level access control, not resource-level ABAC.

5. 🧩 Custom Permission Claims via Script Mapper

"permissions": {
  "documents": ["read", "write"],
  "reports": ["read"],
  "admin-panel": []
}

How it works: Use a Keycloak Script Mapper to compute a permission map at token-generation time, injecting it as a custom claim.

Pros Cons
Token is self-contained — no PDP call at runtime Permissions are frozen at token-issue time
Resource server has zero policy knowledge
Fully customizable format		 Script runs on every token issuance (perf cost)
Can't encode dynamic context changing per-request
Verdict: ⚠️ Pragmatic for semi-static permissions, but loses ABAC's dynamic nature.

6. 🌐 External Authorization (No Permissions in Token)

Token: contains identity only (sub, name, email)
↓
Request hits your API
↓
API calls external PDP (OPA, Cedar, Keycloak) with {user, resource, action, context}
↓
PDP returns allow/deny

How it works: Every access decision is delegated to an external Policy Decision Point (PDP) at request time. Common engines include OPA, AWS Cedar, or Keycloak's token endpoint.

Pros Cons
Token stays small and simple Every request requires a PDP round-trip (latency)
Permissions are always real-time, never stale
Full context available (time, IP, device)		 PDP becomes critical dependency (availability risk)
More infrastructure to manage
Verdict: ✅ Best for high-security, dynamic environments. This matches the current Keycloak flow using response_mode=decision.

Recommendation: Your current setup is very well designed. It uses a hybrid of:
  1. Attributes in the token (department, clearance_level) — so the PDP has user context.
  2. Keycloak PDP evaluation (response_mode=decision) — so policies are centralized and dynamic.
