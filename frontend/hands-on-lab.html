Attribute-Based Access Control (ABAC) in Keycloak

Learn how to build fine-grained, dynamic, and context-aware security policies using user, resource, and environment attributes in Keycloak.

5. Hands-on Lab: Configure Keycloak ABAC

Follow this detailed lab to set up a working Keycloak instance, configure ABAC parameters, and deploy a policy that matches user clearance to resource requirements.

Prerequisites

You need Docker and Docker Compose installed on your machine.

Step 1: Build and Start Keycloak 26 with Pre-Bundled Scripts

In Keycloak 26, the legacy upload-scripts feature is completely removed for security. JavaScript authorization policies must now be pre-packaged inside a custom provider JAR file and deployed to Keycloak's /opt/keycloak/providers/ directory, while explicitly enabling the scripts feature flag.

The lab now uses a multi-stage Docker build to package the JavaScript policy into a provider JAR, and a Compose stack with PostgreSQL for persistent realm data. Review the lab-code/Dockerfile and lab-code/docker-compose.yml files provided in the lab directory:

lab-code/Dockerfile 
# Bundles policy script and META-INF descriptor into a JAR provider
FROM alpine:latest AS builder
RUN apk add --no-cache zip
WORKDIR /build
COPY abac-policy.js .
COPY META-INF ./META-INF
RUN zip -r abac-policy-provider.jar abac-policy.js META-INF

FROM quay.io/keycloak/keycloak:26.6.2
COPY --from=builder /build/abac-policy-provider.jar /opt/keycloak/providers/
ENV KC_FEATURES=scripts
RUN /opt/keycloak/bin/kc.sh build
lab-code/docker-compose.yml 
services:
  postgres:
    image: postgres:16
    container_name: keycloak_abac_db
    environment:
      POSTGRES_DB: keycloak
      POSTGRES_USER: keycloak
      POSTGRES_PASSWORD: keycloak
    volumes:
      - postgres_data:/var/lib/postgresql/data

  keycloak:
    build: .
    container_name: keycloak_abac_lab
    environment:
      - KEYCLOAK_ADMIN=admin
      - KEYCLOAK_ADMIN_PASSWORD=admin
      - KC_DB=postgres
      - KC_DB_URL=jdbc:postgresql://postgres:5432/keycloak
      - KC_DB_USERNAME=keycloak
      - KC_DB_PASSWORD=keycloak
      - KC_FEATURES=scripts
      - KC_HTTP_ENABLED=true
      - KC_HOSTNAME_STRICT=false
    ports:
      - "8080:8080"
    depends_on:
      - postgres
    command: start

volumes:
  postgres_data:

From the lab-code/ directory, build the custom image and start the stack:

cd lab-code
docker compose up --build -d
Persistence Note: This Compose stack uses PostgreSQL with a named Docker volume, so your realm, users, and authorization configuration survive container restarts. If you run docker compose down -v, the postgres_data volume is removed and you will need to re-create the realm, client, users, resources, and policies.

Step 2: Access the Admin Console and Configure Client

  1. Open browser to http://localhost:8080 and log in with admin/admin.
  2. Create a Realm named abac-realm.
  3. Navigate to Clients and create a Client:
    • Client ID: document-service-api
    • In the Capability config section, configure:
      • Client authentication: ON (Confidential client)
      • Authorization: ON (Enables Authorization Services)
      • Direct access grants: ON (Required for resource owner password credentials flow)
  4. Click Save. You will now see an Authorization tab on the client details page.
  5. Go to the Credentials tab on the client details page and copy the value of the Client secret. You will need this client secret for the API requests in Step 9.

Step 3: Configure User Profile Schema for Custom Attributes

By default, Keycloak 26 enforces a strict **User Profile Schema**. You cannot add custom attributes like department or clearance_level to a user unless they are first declared in the Realm's User Profile configuration.

  1. In the left sidebar, navigate to Realm settings.
  2. Click on the User profile tab (ensure you are on the Attributes sub-tab).
  3. Define the department attribute:
    • Click Create attribute.
    • Attribute name: department
    • Display name: Department
    • In the Permissions section, select:
      • Who can edit: Admin (Users should not be allowed to change their own department)
      • Who can view: Admin and User
    • Click Save.
  4. Define the clearance_level attribute:
    • Click Create attribute.
    • Attribute name: clearance_level
    • Display name: Clearance Level
    • In the Permissions section, select:
      • Who can edit: Admin
      • Who can view: Admin and User
    • Click Save.

Step 4: Map User Attributes into a Client Scope

Defining custom user attributes is not enough on its own. To make those values available to tokens and authorization evaluations, add them as user attribute protocol mappers in a client scope, then assign that scope to the client.

  1. In the left sidebar, navigate to Client scopes and click Create client scope.
  2. Create a scope named abac-attributes and save it.
  3. Open the new abac-attributes scope and go to Mappers.
  4. Create a mapper for department:
    • Mapper type: User Attribute
    • Name: department
    • User Attribute: department
    • Token Claim Name: department
    • Claim JSON Type: String
    • Enable Add to access token.
  5. Create another mapper for clearance_level using the same configuration pattern:
    • Name: clearance_level
    • User Attribute: clearance_level
    • Token Claim Name: clearance_level
    • Claim JSON Type: String
    • Enable Add to access token.
  6. Go to Clients -> document-service-api -> Client scopes and assign abac-attributes as a Default client scope.
    If you prefer to keep it optional, assign it as an optional scope and request it explicitly with scope=openid profile abac-attributes during login.

Step 5: Setup User Attributes and Profile

Create two users to test access permissions. Due to Keycloak 26's default **User Profile** policies, basic fields must be fully completed to allow API logins without encountering "Account is not fully set up" errors.

  1. Create user: alice
    • Username: alice
    • Email: alice@example.com
    • First Name: Alice
    • Last Name: Smith
    • Email verified: Toggle **ON**
    • Required user actions: Ensure this field is **empty** (no actions like Update Password or Verify Email listed)
    • Once the user is created, since department and clearance_level are defined in the User Profile schema, they will appear directly as custom input fields on the user details page (under the Details tab). Populate them as:
      • Department: hr
      • Clearance Level: 3
      Note: If they do not appear on the Details form, navigate to the **Attributes** tab and add them as key-value pairs.
  2. Create user: bob
    • Username: bob
    • Email: bob@example.com
    • First Name: Bob
    • Last Name: Jones
    • Email verified: Toggle **ON**
    • Required user actions: Ensure this field is **empty**
    • Configure his custom attributes on the user details page (under the Details tab):
      • Department: eng
      • Clearance Level: 1
  3. Set password credentials for both users:
    • Go to the **Credentials** tab for each user.
    • Click **Set password** (or Reset password).
    • Password: password
    • Set **Temporary** to **OFF** (this is critical for direct login API).
    • Click **Save** / **Set password**.

Step 6: Define Authorization Scopes, Resources & Attributes

Authorization Scopes represent actions that can be performed on a resource (e.g., read, write, delete). These are separate from OAuth2 scopes like openid profile. We define scopes first, then create resources and associate scopes with them.

6a. Create Authorization Scopes

  1. Go to Client: document-service-api -> Authorization -> Scopes.
  2. Click Create authorization scope and create each of these:
    • Name: read — Click Save
    • Name: write — Click Save
    • Name: delete — Click Save
Concept: Think of scopes as verbs and resources as nouns. Combined they express "user can read the Secret HR Report" or "user can delete the Secret HR Report". Without scopes, permissions are binary — full access or no access.

6b. Create a Resource with Scopes and Attributes

  1. Go to Client: document-service-api -> Authorization -> Resources.
  2. Create Resource:
    • Name: Secret HR Report
    • Type: document
    • URI: /documents/hr/secret
    • Authorization scopes: Select read, write, and delete
    • Add Attributes: Key = department, Value = hr
    • Add Attributes: Key = classification_level, Value = 3
  3. Click Save.

Step 7: Register the Pre-Bundled JavaScript Policy

Because our custom policy has been packaged and registered in lab-code/META-INF/keycloak-scripts.json, Keycloak 26 makes it available in the console by default. You do not need to copy-paste code into the browser.

  1. Go to client's Authorization -> Policies -> Create Policy.
  2. Look for our pre-registered policy under the dropdown list. Select **Verify Dept and Clearance ABAC Policy** (the name matches the registry entry).
  3. Give it a local name: Verify Dept and Clearance ABAC Policy.
  4. Click Save.

Step 8: Create Permission Bindings

We now create two types of permissions that bind resources and scopes to our ABAC policy. This demonstrates the difference between resource-level and scope-level access control.

8a. Resource-Based Permission (Full Access Gate)

This permission controls whether the user can access the resource at all. If denied, none of the scope-based permissions matter.

  1. Go to client's Authorization -> Permissions -> Create Permission.
  2. Select Resource-based Permission.
  3. Fill out:
    • Name: Secure Document Access Permission
    • Resources: Select Secret HR Report
    • Policies: Select Verify Dept and Clearance ABAC Policy
  4. Click Save.

8b. Scope-Based Permissions (Action-Level Control)

Scope-based permissions control which actions a user can perform on a resource. For example, you might allow all matching users to read, but only managers to write or delete.

First, create a simple Role Policy for managers:

  1. Go to client's Authorization -> Policies -> Create Policy.
  2. Select Role.
  3. Fill out:
    • Name: Require Manager Role
    • Realm Roles: Select default-roles-abac-realm, then click the X to remove it, and type/select the role you want. If you haven't created a manager realm role yet, create one first via Realm roles -> Create role -> Name: manager.
    • Realm Roles: Select manager
  4. Click Save.

Assign the manager role to Alice (so she can write/delete):

  1. Go to Users -> alice -> Role mapping.
  2. Click Assign role, select manager, and click Assign.
  3. Do NOT assign manager to Bob — he will only get read access if his ABAC attributes match.

Now create the scope-based permissions:

  1. Go to client's Authorization -> Permissions -> Create Permission.
  2. Select Scope-based Permission.
  3. Create permission for read access:
    • Name: Document Read Permission
    • Resources: Select Secret HR Report
    • Scopes: Select read
    • Policies: Select Verify Dept and Clearance ABAC Policy
    • Decision strategy: Unanimous
  4. Click Save.
  5. Create another scope-based permission for write access:
    • Name: Document Write Permission
    • Resources: Select Secret HR Report
    • Scopes: Select write
    • Policies: Select both Verify Dept and Clearance ABAC Policy AND Require Manager Role
    • Decision strategy: Unanimous (both policies must pass)
  6. Click Save.
  7. Create another for delete access:
    • Name: Document Delete Permission
    • Resources: Select Secret HR Report
    • Scopes: Select delete
    • Policies: Select both Verify Dept and Clearance ABAC Policy AND Require Manager Role
    • Decision strategy: Unanimous
  8. Click Save.
What this achieves:
  • Alice (HR, Clearance 3, Manager role) → gets read, write, delete scopes
  • Bob (Eng, Clearance 1, no Manager role) → gets denied entirely (ABAC attributes don't match)
  • A future HR user with Clearance 3 but no Manager role → gets only read scope

Step 9: Testing the Policy Execution

You can verify access rights using the Keycloak Authorization Endpoint. First obtain an access token that carries the mapped user attributes, then request an authorization decision for the protected resource.

1. Authenticate Alice (Department: HR, Clearance: 3)

# Get Access Token for Alice
curl -d "client_id=document-service-api" \
     -d "username=alice" \
     -d "password=password" \
     -d "grant_type=password" \
     -d "scope=openid profile abac-attributes" \
     -d "client_secret=<YOUR_CLIENT_SECRET>" \
     -X POST http://localhost:8080/realms/abac-realm/protocol/openid-connect/token

If you assigned abac-attributes as a default client scope in Step 4, the explicit scope line is optional. Keep it if you want the request to be unambiguous. Before moving on, decode the token and confirm it includes department and clearance_level.

2. Query keycloak for Resource Authorization Decisions

# Alice requests access to "Secret HR Report" (Clearance 3 required, Dept HR required)
# Push runtime environment claims through claim_token. Raw form fields like
# network_location=office are not exposed to JavaScript policies.
CLAIM_TOKEN=$(printf '%s' '{"network_location":["office"]}' | base64 -w0)

curl -H "Authorization: Bearer <ALICE_ACCESS_TOKEN>" \
     -d "grant_type=urn:ietf:params:oauth:grant-type:uma-ticket" \
     -d "audience=document-service-api" \
     -d "response_mode=decision" \
     -d "permission=Secret HR Report" \
     -d "claim_token=${CLAIM_TOKEN}" \
     -d "claim_token_format=urn:ietf:params:oauth:token-type:jwt" \
     -X POST http://localhost:8080/realms/abac-realm/protocol/openid-connect/token

If Keycloak exposes the mapped user claims and the pushed runtime claim correctly, Alice should receive {"result":true}. If access is denied, inspect the Keycloak container logs because the bundled policy now prints the user attribute keys, context attribute keys, and normalized values it actually evaluated.

3. Repeat with Bob (Department: Eng, Clearance: 1)

When Bob requests access to the Secret HR Report, Keycloak's PDP should return 403 Forbidden because his department does not match and his clearance is insufficient.

If you need to troubleshoot the evaluation, inspect the server logs with docker compose logs -f keycloak from the lab-code/ directory. The bundled policy logs lines such as User Attribute Keys, Context Attribute Keys, and the normalized department/network values to show what Keycloak actually made available during authorization.
